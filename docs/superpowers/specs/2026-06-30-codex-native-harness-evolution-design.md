# Codex 네이티브 하네스와 제한형 검증 루프 설계

## 배경

PromptAgent는 한글 이슈, 역할별 worktree, 독립 검토, 수정 예산, CI와 squash merge를 연결하는 프로젝트 하네스를 이미 사용한다. 그러나 프로젝트 스킬의 현재 위치인 `skills/`는 Codex 공식 저장소 스킬 자동 탐색 경로가 아니므로 세션이 스킬을 직접 발견하지 못한다. 또한 구현 전 계약 고정과 검토자 간 불일치 처리 방식이 문서 관례에 의존한다.

Ouroboros와 Oh My ClaudeCode(OMC)를 조사했지만 전체 설치는 채택하지 않는다. Ouroboros의 Python MCP·이벤트 저장소·실행 루프는 현재 하네스와 책임이 중복되고, OMC는 Claude Code 플러그인·훅·명령 구조와 자동 승인 외부 작업자를 전제로 한다. 두 프로젝트의 유용한 패턴만 Codex 저장소 스킬과 기존 오케스트레이터 계약으로 이식한다.

## 조사 근거

| 대상 | 채택할 패턴 | 채택하지 않을 부분 |
|---|---|---|
| [Codex Skills](https://developers.openai.com/codex/skills) | `.agents/skills/`, 점진적 공개, 명확한 트리거 | 저장소 실험 단계의 성급한 배포 패키징 |
| [Codex Plugins](https://developers.openai.com/codex/plugins/build) | 2~3회 실제 검증 후 플러그인 승격 | 첫 구현부터 marketplace 배포 |
| [Q00/Ouroboros](https://github.com/Q00/ouroboros) | 인터뷰·Seed 고정, 기계→의미→합의 검증, 반복 상태 | 외부 MCP 런타임, 별도 Python Agent OS, 자동 설치 스크립트 |
| [OMC](https://github.com/Yeachan-Heo/oh-my-claudecode) | PRD별 검증 기준, 세션 상태, 모드 소유권, 동일 실패 조기 중단 | Claude 전용 플러그인, 전역 설정, 훅, 자동 승인 외부 CLI |
| Ralphathon 검증 그림 | 공격 시나리오, 독립된 보수·공격 검토, 불일치 판정 | 무제한 반복, 특정 모델을 판정자로 고정 |

## 목표

1. 프로젝트 스킬을 Codex가 자동 발견하는 저장소 경로로 전환한다.
2. 사용자 승인 후 요구사항을 변경 불가능한 실행 계약으로 고정한다.
3. 결정적 검증을 먼저 실행하고 필요한 경우에만 독립 에이전트 검토를 사용한다.
4. 검토자 불일치를 별도 판정자가 근거로 해결한다.
5. 기존 권한·수정 횟수·deadline·이슈 한도를 완화하지 않는다.

## 비목표

- Ouroboros, OMC 또는 원격 MCP를 기본 개발 환경에 설치하지 않는다.
- Claude Code용 명령·훅·상태 파일을 복제하지 않는다.
- 모델 이름을 에이전트 정의에 고정하지 않는다.
- 제품 사용자가 추천받는 에이전트 패키지 실행 기능을 추가하지 않는다.
- 이번 이슈에서 공유 marketplace 플러그인을 배포하지 않는다.

## 구조

### Codex 스킬 위치

`skills/{name}/SKILL.md`를 `.agents/skills/{name}/SKILL.md`로 이동하고 다음 파일의 참조를 함께 변경한다.

- `agents/*.md`: 에이전트가 사용할 스킬 이름은 유지한다.
- `tests/harness/validate-harness.mjs`: canonical 경로를 `.agents/skills/`로 변경한다.
- 아키텍처·운영 문서: 프로젝트 스킬 위치와 탐색 규칙을 갱신한다.

호환용 복사본이나 같은 이름의 중복 스킬은 두지 않는다. Codex는 같은 이름을 병합하지 않으므로 단일 canonical 경로가 필요하다.

### 명세 결정화

새 `spec-crystallization` 스킬은 구현 시작 전에 `_workspace/01_seed_contract.md`를 만든다. 계약은 다음 필드를 포함한다.

- 이슈·목표·사용자 가치
- 범위와 비목표
- 파일·모듈 소유 경계
- 구체적이고 명령으로 확인 가능한 완료 조건
- 권한·데이터·보안 위험
- 검증 명령과 증적 위치
- 승인 시각과 SHA-256 계약 해시

저장소에서 확인할 수 있는 사실은 사용자에게 묻지 않는다. 사용자 판단이 필요한 모호성만 한 번에 하나씩 질문한다. 승인 후 원본 계약을 조용히 수정하지 않으며 변경이 필요하면 `_workspace/01_seed_amendment-{n}.md`에 이유, 영향, 재승인을 기록한다.

### 제한형 적대적 검증

새 `adversarial-verification` 스킬과 네 역할을 추가한다.

| 역할 | 책임 |
|---|---|
| `verification-attacker` | 완료 조건과 이전 결함을 바탕으로 실패 시나리오를 만든다. |
| `evidence-guardian` | 증거가 부족하면 통과시키지 않는 보수적 검토를 수행한다. |
| `solution-challenger` | 맥락 추론과 대안을 사용해 누락·과설계·더 나은 해법을 찾는다. |
| `verification-judge` | 두 검토가 불일치할 때만 원본 계약과 실행 증거로 판정한다. |

하나의 검증 사이클은 다음 순서를 따른다.

1. 테스트·빌드·정적 규칙·diff 검사를 실행한다. 실패하면 에이전트 토론 없이 구현 소유자에게 반환한다.
2. 첫 사이클에 최대 10개 공격 시나리오를 생성한다.
3. `evidence-guardian`과 `solution-challenger`가 서로의 결론을 보지 않고 같은 계약·diff·기계 증거를 검토한다.
4. 두 결론이 같으면 해당 결론을 사용한다. 불일치할 때만 `verification-judge`가 판정한다.
5. 실패가 수정 예산 안에 있으면 소유자에게 반환하고, 다음 사이클은 신규·영향 시나리오를 최대 5개 추가한다.
6. 같은 실패가 두 사이클 연속 반복되거나 전체 수정 2회를 사용하면 `blocked`로 종료한다.

라이브 실행은 최대 15개 시나리오만 사용한다. 이미지의 50개 목표는 장기 오프라인 eval corpus의 승격 기준으로만 사용해 현재 60분 deadline과 충돌하지 않게 한다.

### 상태와 증적

검증 산출물은 다음 경로에 보존한다.

```text
_workspace/
├── 00_authority_manifest.md
├── 01_seed_contract.md
├── verification/
│   ├── cycle-01-scenarios.md
│   ├── cycle-01-guardian.md
│   ├── cycle-01-challenger.md
│   ├── cycle-01-judge.md
│   └── cycle-01-result.md
└── 99_run_summary.md
```

각 결과에는 입력 SHA, 실행 명령, exit code, 검토 결론, 수정 예산, 다음 상태를 기록한다. 숨겨진 추론은 저장하지 않고 관찰 가능한 근거와 판정 이유만 남긴다.

## 오케스트레이터 통합

`project-orchestrator`의 architecture 단계 앞에 명세 결정화를 배치하고, integration 검증을 제한형 적대적 검증으로 교체한다. 기존 구현자·독립 reviewer 구조는 유지하며 다음 소유권 규칙을 추가한다.

- 명세 결정화가 실행 계약을 소유한다.
- 구현자는 자기 결과를 검토하거나 판정하지 않는다.
- 판정자는 불일치가 없으면 호출하지 않는다.
- 적대적 검증은 수정 예산을 새로 만들지 않고 기존 2회 예산을 공유한다.
- PR·merge·close·deploy 권한은 검토 에이전트가 아니라 authority manifest가 결정한다.

## 오류 처리와 중단 조건

- 기계 검증 실패: 담당 구현자에게 반환하고 수정 횟수를 1 증가시킨다.
- 한 검토자 실패: 1회만 재호출하고 재실패는 `미검증`으로 기록한다.
- 검토 불일치·판정자 실패: 자동 통과시키지 않고 `blocked`로 종료한다.
- 같은 실패 반복: 두 번째 동일 실패에서 조기 중단한다.
- deadline 또는 수정 예산 초과: 추가 에이전트를 호출하지 않는다.
- 사용자 중단: 현재 증적을 보존하고 외부 쓰기를 중지한다.

## 테스트 전략

1. 하네스 구조 테스트가 `.agents/skills/`와 새 에이전트·스킬을 검증한다.
2. 스킬별 should-trigger 8개, should-not-trigger 8개를 fixture로 검증한다.
3. 명세 해시와 amendment 불변식을 결정적 스크립트 테스트로 검증한다.
4. 기계 실패 시 검토자 미호출, 검토 일치 시 판정자 미호출, 불일치 시 판정자 호출을 드라이런 fixture로 검증한다.
5. 기존 governance·Spring·React 테스트를 회귀 실행한다.
6. 실제 후속 이슈 2~3개에서 호출 횟수, 수정 횟수, false positive, 소요 시간을 기록한다.

## 플러그인 승격 기준

다음 조건을 모두 만족한 뒤 별도 이슈로 `promptagent-harness` Codex 플러그인을 만든다.

- 실제 이슈 3개에서 명세·검증 루프가 완료된다.
- 무한 반복, 권한 확대, 동일 스킬 중복 탐색이 없다.
- 트리거 경계 테스트가 모두 통과한다.
- 평균 검토 사이클이 2 이하이고 판정자 호출 사유가 추적 가능하다.
- 프로젝트 외부에서도 필요한 경로와 명령을 설정으로 주입할 수 있다.

플러그인은 `.codex-plugin/plugin.json`과 skills만 우선 포함한다. MCP·앱·훅은 측정된 필요가 생기기 전까지 추가하지 않는다.

## 롤백

`.agents/skills/` 전환에 문제가 있으면 이동 커밋을 되돌려 기존 `skills/` 경로와 테스트를 복구한다. 새 검증 루프는 오케스트레이터 연결을 제거하면 기존 독립 QA 흐름으로 돌아간다. 외부 런타임이나 데이터베이스를 설치하지 않으므로 별도 시스템 제거 작업은 없다.

## 결정

첫 단계는 외부 도구 설치가 아닌 저장소 로컬 스킬 이식이다. 전체 런타임을 추가하기 전에 현재 하네스의 탐색 가능성, 명세 불변성, 불일치 판정과 중단 조건을 강화하고 실제 이슈의 측정 결과로 플러그인 승격을 판단한다.
